# Реестр спецификаций — Цифровой деканат (Dekanat)

Каталог `specs/` содержит спецификации задач для управляемой спецификациями соло-разработки (Spec-Driven Development) с использованием автономных ИИ-агентов в рамках конкурса *MGIMO × AI Challenge* (трек Vibe-Coding). Система спецификаций обеспечивает строгую изоляцию контекста, предотвращает расползание скоупа (scope creep) и гарантирует прозрачную верификацию каждого этапа разработки перед дедлайном 22.11.2026.

## 2. Правила рабочего процесса (Workflow Rules)

1. **Единственный активный тикет**: В файле `docs/STATE.md` всегда указан ровно **один** активный тикет. Он является единственным источником правды для следующего шага работы.
2. **Приоритет спецификации**: Перед началом написания кода агент или разработчик обязан изучить спецификацию активного тикета `specs/TICKET-<NN>-<slug>.md`.
3. **Границы скоупа**: Разработка ведется строго в рамках раздела `Scope`. Любые идеи, не входящие в текущий скоуп, заносятся в раздел `Deferred ideas` спецификации, а не в кодовую базу.
4. **Процедура закрытия тикета**:
   - Спецификация переносится в `specs/archive/TICKET-<NN>-<slug>.md`.
   - В спецификацию добавляется раздел `Result` с перечнем реализованных решений, доказательствами верификации и обоснованными отклонениями.
   - В `docs/STATE.md` активируется следующий тикет.
   - В `docs/CHANGELOG.md` вносится запись о релизе/изменениях.
5. **Фиксированный порядок**: `01 [DONE] → 02 [DONE] → 03 [ACTIVE] → 04 [OPEN, MAX Mini App] → 06 → 07 → 08` (TICKET-05 пропущен).

## 3. Шаблон критериев приёмки (Definition of Done Template)

Каждый критерий `Done-When` в спецификациях должен быть детерминированным и проверяемым:
- **Командой в терминале** (например, `pnpm typecheck`, `pnpm test`, `curl -I https://...`);
- **Пошаговым воспроизводимым сценарием (Click-path)** с ожидаемым результатом в интерфейсе;
- **Скриншотом или артефактом отчёта**, сохранённым в репозитории.
